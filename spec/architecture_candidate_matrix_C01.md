## H1 — image-token tile-tail cost

- **Problem.** A fixed PE tile may make the narrow remainder for `N=66/70` inefficient relative to widths near 60/64.
- **Observed evidence and class.** Host graph metadata records image-prefill `ffn_up-0` at `N=60×1,64×4,66×1,70×10` in the selected observations. The host arithmetic-only tile screen reports 97.3% useful columns for `T=8`, 90.2% for `T=16`, 78.6% for `T=32`, 62.6% for `T=64`, and 52.8% for `T=128`. These are shape and arithmetic-padding observations, not timing, DDR traffic, PL stalls, or a K26 failure interval. See `/home/zhiro/research/kv260-vlm/literature/kv260_vlm_falsifiable_hypotheses_20260923.md` and `/home/zhiro/research/kv260-vlm/status/PROJECT_STATUS.md`.
- **Mechanism and hardware structure.** One fixed PE array processes the supported Q4_K×F32→F32 image-prefill job with a chosen column tile, tail predication or padded tile. A shape-specific descriptor table is conventional; no custom mechanism is established.
- **Changed decision variable.** Tile width / tail policy per job. `N` is already available to the static backend selector before scheduler compute-buffer allocation according to `/home/zhiro/research/kv260-vlm/spec/runtime_shape_visibility_audit_20260923.md`. No additional decision input has been observed, so an `N` lookup alone is not incremental.
- **Closest prior-art competitor.** Memory-Centric VLM covers matrix-level dispatch and tiled data movement; StreamTensor covers compiler-driven tiling/layout conversion; ReCoVLM uses two-shape visual-token normalization. The latter's LLaVA/Orin/VU9P result is not a KV260/MiniCPM-V comparator, but fixed-shape normalization must be included as a control where applicable. See `/home/zhiro/research/kv260-vlm/literature/independent_novelty_review.md` and `/home/zhiro/research/kv260-vlm/literature/notes/recovlm.md`.
- **Strongest static control.** Exhaustively tune a single tile and static per-phase or `N`-keyed tables across legal tiles (including `T=8`); include tail predication, padding, fixed buckets/two-shape normalization, movement/fusion, overlap, CPU fallback and identical quality. Charge shape conversion, descriptor, launch, DMA, synchronization and transition costs. This matches the strongest control specified in the frozen H1 brief.
- **Expected benefit.** Fewer padded columns or reduced tail tile work; benefit exists only if it reduces measured target latency/energy after setup, transfers and CPU/PS costs.
- **Resource, area and runtime cost.** Additional tile options/descriptors or tail control may add LUT/control, local buffering/fragmentation and loop/launch overhead. No placed design, resource report, usable memory measurement, or board cost exists; no area or speedup estimate is supportable.
- **Required real trace.** Exact executed K26 job `M/N/K`, dtype/strides, selector inputs at the decision point, tile descriptors and per-tile cycles; PS submit/sync, AXI bytes/stalls, tail cycles, output visibility, request phase boundary, full input→first-token/done, quality, energy and failures. Include `N=60/63/64/66/70` plus the mixed ordered pattern `[64,70,70,70,70,70,70]` and repeated `5×70`/`5×63` cases.
- **Numeric success threshold proposal (not preregistered).** Against the best static tile/bucket on a frozen held-out request set: at least 5% lower paired median full-request input→first-token latency for the `N=66/70` subgroup and at least 3% lower paired median input→done across the full set, with paired 95% CI excluding zero for the primary measure; soft accuracy no more than 1.0 absolute percentage point below CPU reference. Also report energy and unsupported/fallback requests. These values are a proposal, not a project gate; sample size and quality protocol must be frozen before a future experiment.
- **Direct falsification result.** Reject if fixed `T=8`/best static buckets tie within uncertainty; if the backend fails to preserve/act on `N`; if no extra PL launch/traffic/stall appears for a tail; or if end-to-end cost erases any tile saving. Present evidence already shows `N` is a static selector input and fixed `T=8` cuts arithmetic padding to 2.7%, so the present `N`-only policy does not survive comparison.
- **Minimum viable experiment.** Only after a separate authorized task supplies a real K26 PL path: on the same frozen requests compare the best fixed tile, fixed `T=8`, best `N`-bucket table, and any proposed tail policy with randomized paired order. Capture per-tile, PS/PL, traffic/stall, quality/energy and full-request measurements. First collect the CPU-only K26 reference recommended in the handoff; this C01 task executes neither step.

## H2 — cross-group vision-weight reuse

- **Problem.** Repeated crop/image groups might reload the same vision weights, while batching equal-shape groups could reuse each loaded tile until staging pressure causes a spill or occupancy loss.
- **Observed evidence and class.** The host TextVQA visual inventory contains seven ordered image-encode patterns with 3/5/7 groups. This is a post-processor log inventory. Host graph and allocator observations do not prove that groups are independently schedulable, that weights are fetched repeatedly from external DDR, or that local storage spills at a finite group size. No target failure interval is observed. See `/home/zhiro/research/kv260-vlm/status/PROJECT_STATUS.md` and `/home/zhiro/research/kv260-vlm/literature/kv260_vlm_falsifiable_hypotheses_20260923.md`.
- **Mechanism and hardware structure.** A fixed weight-stationary matrix engine with bounded activation/output staging and double buffers groups same-shape crop work so a weight tile can serve multiple independent lanes before eviction.
- **Changed decision variable.** Crop group size `g` by shape class (possibly selected from metadata and currently available staging capacity). Neither a real selector signal at the required time nor a non-static selection advantage has been demonstrated.
- **Closest prior-art competitor.** UniVLM shares matrix hardware across ViT/LLM stages; Memory-Centric VLM covers movement reuse, dispatch and overlap; conventional cross-batch reuse is established. ReCoVLM's expert-to-DDR-bank-group placement is adjacent for MoE traffic and cannot establish this vision-crop opportunity.
- **Strongest static control.** Compare serial crop execution with fixed double buffers, fixed max group with padding, fixed equal-shape buckets, one development-tuned constant group size, and CPU-only fallback. Give each arm identical prepacking, data layout, DMA overlap, quality and tuning budget. Charge all conversion and transition costs.
- **Expected benefit.** Reduce measured external weight bytes by keeping a tile resident across independent crop work; a byte reduction without latency or energy improvement is not sufficient.
- **Resource, area and runtime cost.** Activations, outputs, descriptors and double buffers compete for usable BRAM/URAM and PE ports; oversubscription can force DDR spills, extra DMA or less concurrency. Aggregate K26 BRAM+URAM is about 2.883 MiB before logic, ports and staging, so usable capacity is not inferred from total. Runtime costs include crop grouping, padding, descriptor setup, DMA, synchronization, fallback and output ordering. No area/fit estimate is available.
- **Required real trace.** Board-side actual graph execution and crop/batch identity/order; exact same-weight reuse distance; bytes and addresses per weight fetch; activation/output liveness and local-memory occupancy; AXI traffic/stalls, DMA and PS time; phase and full-request timing, energy, quality and failure rate. Include observed 3/5/7 and mixed shapes.
- **Numeric success threshold proposal (not preregistered).** Against the best fixed group/bucket control, at least 10% fewer externally observed weight bytes and at least 5% lower paired median full-request input→first-token plus 3% lower input→done latency, with paired 95% CI excluding zero for the primary measure; no quality loss exceeding 1.0 absolute percentage point and no increase in request failure rate. This is a proposal only.
- **Direct falsification result.** Reject if executed traces show no repeated external weight traffic to save; if the maximum fixed/equal-shape group ties the dynamic policy; if staging does not fit without spill; or if bytes fall but full-request latency/energy does not improve after PS–PL costs. There is currently no evidence against these null results.
- **Minimum viable experiment.** After separate task authorization and a working PL path, first instrument actual repeated vision jobs and external weight bytes on one representative 3-, 5- and 7-group request, with a fixed static group-size control. Do not build a group scheduler unless that trace demonstrates a repeatable traffic/staging crossover; C01 performs no board/RTL work.

## H3 — repeated-subgraph PS–PL command replay

- **Problem.** Per-op submit/wait overhead might leave the PL idle across repeated image-encoder groups, making some 3/5/7-group requests control-bound.
- **Observed evidence and class.** Host visual logs and graph shapes suggest repeated image groups. No K26 PS submit/doorbell/interrupt/wait, PL busy/idle interval, descriptor sequence, or replay preparation cost exists. The 3/5/7 workload counts are not evidence of a command gap or a finite latency failure interval.
- **Mechanism and hardware structure.** On a fixed bitstream, submit one prepared command list per repeated image-group sequence or replay a fixed sequence template with addresses patched for the current inputs. The proposed variable is command granularity / template chosen for a sequence, not a new accelerator datapath.
- **Changed decision variable.** Per-op vs per-group command batching and sequence-template selection. A static command list per known shape bucket can make the same selection; no metadata or sequence transition requiring a dynamic decision has been observed.
- **Closest prior-art competitor.** Memory-Centric VLM's matrix-level dispatch; GLITCHES load instruction aggregation; StreamTensor's generated transfer/runtime pipeline; and GPU graph replay in the single-request VLM runtime literature. Generic launch aggregation has high prior-art overlap.
- **Strongest static control.** Compare per-matrix launch, one matrix-level command, maximum legal static batch, a fixed pre-recorded command list per shape bucket, and a persistent pipeline where legal. Use identical buffers/layout/fusion/DMA overlap/CPU fallback. Charge command preparation, address patching, synchronization, setup and failures.
- **Expected benefit.** Reduce measured PS submit/wait gaps and PL idle time. It is useful only if that translates to an end-to-end request gain and does not move work onto a slower CPU/descriptor path.
- **Resource, area and runtime cost.** Command buffers/ring descriptors and patch state consume DDR/BRAM and host memory; control logic, queue depth, dependencies, address patching, synchronization, setup and error recovery add LUT and host time. No implementation or resource data exists.
- **Required real trace.** Matched board PS timestamps for submit, doorbell, interrupt, wait and completion; PL busy/idle cycles; DMA descriptor and sequence hashes, addresses and shape changes; complete request timeline and setup; CPU overhead, traffic, energy, quality and failures. Separate cold setup from steady-state execution.
- **Numeric success threshold proposal (not preregistered).** Versus the strongest fixed command-list/batch control, at least 30% reduction in measured PS submission+wait time and at least 5% lower paired median full-request input→first-token plus 3% lower input→done latency, with paired 95% CI excluding zero for the primary measure; soft accuracy within 1.0 absolute percentage point and no increase in failures. This is only a future screen proposal.
- **Direct falsification result.** Reject if command gaps are under 5% of full request time, PL stays busy through apparent host spans, fixed replay ties, sequence/address patching consumes the saved time, or full-request latency does not improve. Current evidence gives no command-gap share.
- **Minimum viable experiment.** Once a separately authorized PS–PL implementation exists, trace one actual repeated sequence and one fixed-bucket command-list control end-to-end, including patch/setup and all waits. Stop if command gaps are not a material full-request component. C01 neither implements nor runs this experiment.

## H4/H5 screen; not promoted

- **H4: vision-to-language materialization/local-memory threshold.** The host graph suggests an F32 embedding and an arithmetic/logical size bound, but no real runtime boundary trace proves an extra PS–PL/DDR copy, local-memory spill, or producer/consumer serialization. UniVLM/StreamTensor movement and fusion plus ReCoVLM compression-before-transfer are strong competitors. Do not claim a threshold or propose a new buffer allocator from host virtual ranges.
- **H5: CMA admission/fallback cliff.** No inference-time allocation failure or shape-correlated CMA latency cliff is observed. Earlier low-CMA observations coincided with updater activity; after reboot the reported CMA free amount was above the stated floor and no inference ran. Static max-pool, fixed ring and CPU fallback are the strong controls; static cache/ring residency is already prior art. Do not rename allocator or static residency work.

Neither H4 nor H5 has an observed finite failure interval or a decision variable shown to exceed static controls, so they are screened out rather than expanded into candidates.
