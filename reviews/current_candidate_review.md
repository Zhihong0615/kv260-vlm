## Ten-question adversarial audit

1. **Renaming of known mechanisms.** H1 is ordinary shape/tile dispatch and tail handling; H2 is batching, weight reuse, and double buffering; H3 is launch aggregation or command replay. H4 is standard producer/consumer fusion, conversion, or buffering; H5 is static allocation admission/cache residency. Renaming these as a K26 “planner” does not create a new mechanism. The frozen novelty review explicitly rejects broad phase specialization, movement, fusion, persistent state, and bank/port allocation claims.

2. **Prior-art overlap.** ReCoVLM covers phase assignment, two-shape visual-token normalization, transfer reduction, static sink/ring KV residency, and expert bank-group placement. StreamTensor covers tiling, layout conversion, fusion, FIFO sizing, DMA and host runtime generation. Memory-Centric VLM covers matrix-level dispatch and movement/overlap; GLITCHES aggregates small load instructions; TRINE covers runtime mode and DAG scheduling. These papers use different platforms and models, so they do not prove KV260 performance, but they make the generic mechanisms poor novelty claims. The C01 matrix itself correctly treats H1–H3 as falsification cases, not passing methods.

3. **Workload representativeness.** The workload evidence is TextVQA dev50 plus a few selected host traces: three phase-timeline requests, four graph/allocator requests, and seven logged image-token patterns. Those support shape coverage and measurement priorities, not a deployment distribution, held-out result, or board workload population. The visual patterns are post-processor logs; pre-dispatch availability, crop semantics, and independent job identity are not proven.

4. **Evidence-to-claim support.** H1 has host graph widths and an analytical padding calculation, not K26 tile cycles, AXI traffic, or tail stalls. H2 has group counts and virtual host-buffer metadata, not physical weight rereads, last-use events, or local-store high-water marks. H3 has host graph patterns, not A53/XRT submit/wait or PL busy/idle traces. H4's estimated tensor size is conditional arithmetic, not an observed copy/materialization. H5 has no inference run. Host shape, callback, or allocator records do not support physical occupancy, PS–PL cost, or a full-board speedup.

5. **Baseline strength.** The frozen candidate matrix names appropriate strong controls: H1 fixed/per-phase/`N`-keyed tiles, `T=8`, fixed buckets, predication and CPU fallback; H2 serial work with double buffering, fixed maximum/equal-shape groups and a tuned constant; H3 matrix-level submit, maximum legal batching, fixed command lists and persistent pipeline where legal. These are the right controls, but none was measured against a candidate on K26. Comparing with a weak all-GEMM, unbatched, or unbuffered path would not establish a contribution.

6. **Transition and full-request cost.** Candidate/hypothesis sheets call for charging DMA, layout conversion, setup, descriptors, synchronization, address patching, fallback, and overlay transitions. Those costs are proposed measurements, not observed values. No full-request K26 timeline exists. The selected host timelines place most time in combined vision/projector spans, but that host share cannot be projected to K26; it does make an isolated image-prefill kernel win insufficient evidence without full-request measurement.

7. **Simpler alternatives.** H1 can use a static `N` lookup because the pinned runtime exposes tensor dimensions before backend scheduler-buffer allocation. H2 can use a fixed equal-shape group size or maximum padded batch with double buffering. H3 can use one fixed replay list per shape bucket or the largest legal static command batch. H4 can use a pre-sized buffer, bulk handoff, or static fused pipeline. H5 can use a fixed pool/ring and CPU fallback. No candidate shows a decision case that these controls cannot cover.

8. **Evidence class.** The decision-relevant workload and performance evidence is host-measured, host graph metadata, host virtual-buffer metadata, or analytical-from-host-trace. Prior-art performance figures are platform-specific (including U55C/VU9P/Orin and other KV260 models) and cannot be transplanted to MiniCPM-V/KV260. The frozen record has no target board VLM inference, custom PL execution, placed candidate, physical DDR/AXI trace, or measured PS–PL boundary.

9. **Numeric falsifiability.** H1–H3 propose observable metrics and rejection rules, so they can guide future experiments, but the bars are explicitly not frozen and conflict between A01 and C01. Examples: H1 C01 proposes ≥5% subgroup TTFT and ≥3% full-set completion gain, while A01 Q1 applies a ≥10% request-level bar plus ≥15% PS+PL-cost reduction; H2 C01 proposes ≥10% fewer weight bytes and 5%/3% TTFT/completion gains, while A01 Q2 asks for ≥20% fewer reads and the shared 10% request-level bar; H3 C01 proposes ≥30% PS submit/wait reduction and 5%/3% request gains, while A01 Q4 uses ≥25% PS wait/PL-idle reduction plus the shared 10% bar and a preparation-cost limit. The shared A01 quality/held-out bar is itself proposed, not preregistered. H2's 80%-of-usable-local-memory condition also needs an actually measured post-interface usable capacity. These differences must be resolved before a future test can receive a pass/fail judgment; none of the proposed numbers is achieved evidence.

10. **Failure boundary.** The documents state sensible ways each idea could fail, but no *observed* finite failure interval exists: H1 has width variation without K26 excess cost; H2 has no measured repeated-read/staging boundary; H3 has no measured command gap; H4 has no observed materialization/spill; H5 has no clean CMA admission cliff. Candidate success bars are hypotheses for future experiments, not evidence that a failure regime or benefit already exists.
